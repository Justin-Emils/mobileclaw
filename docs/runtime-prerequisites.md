# 运行时前提：前台、后台、以及步数的代价

这份文档回答三个每次用都会遇到、但从没写下来的问题：

1. **执行一条指令时，谁必须在前台？**
2. **能不能后台跑？**
3. **一条指令要调用几次模型？**

写下来的理由是：这三个答案会**改变你该怎么用它**。不写，每个人都会先踩一次才知道——而其中一次踩坑（切到后台）的后果是**任务停在半路，却不报错**。

---

## 一、谁必须在前台

**两个不同的"前台"，要求不一样。**

| | 必须在前台吗 | 为什么 |
|---|---|---|
| **本应用（MobileClaw）** | **进程必须活着**，画面不必在前 | agent 循环是**这个应用里的 JavaScript**。进程被冻结，循环就停 |
| **被操作的 app**（微信/QQ/…） | **画面必须在前** | `uiautomator dump` 和 `screencap` **只读当前顶层窗口**。它不在前面，读到的就不是它 |

**所以实际操作是**：手机屏幕停在被操作的 app 上，本应用在后台保持进程活着。

### 1.1 "切到后台"指的是**本应用**离开屏幕

**监听的是 `AppState`——也就是 MobileClaw 自己的状态**，不是被操作的 app 的。

**但请注意：监听它不再意味着"离开就中止"。** 早期版本这样做过，现已去掉（理由见 2.1）。下面的表保留下来是因为**它记录了一个必须避开的坑**：平台报告的三种状态里，只有一种是"真的离开"。

| 你做的事 | AppState | 是"真的离开"吗 |
|---|---|---|
| 打开微信（本应用被盖住） | `background` | **是** |
| 按 Home / 进桌面 | `background` | **是** |
| 从最近任务划掉本应用 | `background` | **是**（进程也没了） |
| **下拉通知栏** | `inactive` | **不是** |
| **本应用的审批弹窗出现** | `inactive` | **不是** |
| 来电横幅 / 系统弹窗 | `inactive` | **不是** |
| 分屏（本应用仍可见） | `active` / `inactive` | **不是** |

**`inactive` 为什么必须排除**——这条不是抠字眼，是**会让功能自己掐死自己**：

> **本项目的审批确认框本身就是一个系统绘制的浮层。**

把 `inactive` 当成"离开了"，就会出现：**一个确认框取消了它自己正在询问的那次运行**。一条会在用户自己的界面上触发的规则，不是安全规则。

**另外注意一个反直觉的点**：`"active"` → `"inactive"` → `"background"` 是常见序列。而一个**已经在后台**的应用再收到 `inactive` 时，它**仍然在后台**——如果按"当前状态是否离开"反推"是否在前台"，就会错误地报告"已回到前台"，然后拿着**一份过期的屏幕认知**继续操作。所以"是否在前台"和"当前状态是否离开"必须是**两个独立记录**（这也是我修过的一个真 bug，见 `apps/mobile/test/foreground.test.ts`）。

### 1.2 那个根本张力

仔细想会发现一个矛盾：

- 要看/操作**微信**，微信必须在**前台**
- 但本应用**不在前台**，就有被 Android 冻结或杀掉的风险，而进程没了，驱动一切的 JS 循环也就没了

**所以本应用是"用自己被冻结的风险"来换取"能看见被操作的 app"。**

**这个张力目前是"接受并缓解"，不是"解决"**：

- **缓解**：发送前有两道基于**屏幕本身**的核对（收件人 + 包名），所以**屏幕变了不会做错事**；
- **未解决**：进程真被冻结时，任务**停住且不报错**（见 2.2）；
- **真正的解法**是前台服务——**已评估、明确推迟**，见 2.3。

**你中途切走会怎样**：

- 下一次 `screen_read` 读到的会是**别的 app**
- `screen_open_item` / `screen_send_message` 的核对**会失败** → 拒绝
- **运行不会因此被中止**（早期版本会，现已去掉）
- 如果进程随后被系统冻结，任务**停住且不报错**——这是目前唯一的真实缺口

**不会发生的事**：不会发错人。所有核对工具在屏幕变了之后都只会拒绝。

## 二、能不能后台跑

### 2.1 现在的行为：不中止，继续跑

**切到别的 app（本应用进后台）不会中止运行。** 这是刻意的。

早期版本做过相反的事——一旦本应用离开前台就 `abort()`。**那是错的，理由值得留着**：

> **本应用本来就该在被操作的那个 app 后面。** 手机一次只显示一个 app，所以那个守卫当成"失败"的状态，正是**正常的工作状态**。它唯一可见的效果是：你一打开刚刚让 agent 操作的那个会话，运行就被取消了。

**真正保护不可逆那一步的**是 `screen_send_message` 里的**包名核对**：最后一次读数必须来自调用者指定的那个 app。这是**从屏幕决定的，在按下的那一刻**，而不是从我们自己进程的状态决定的。

**切屏时实际会发生什么**：

| 情况 | 结果 |
|---|---|
| 屏幕上的 app 换了 | 下一步读屏会读到别的 app → `screen_open_item` / `screen_send_message` 的核对**拒绝** |
| 进程被系统冻结或杀掉 | 运行**停住但不报错**（见 2.2） |

**"停住但不报错"这一点没有解决**——见下面的后备选项。可以确定的是：**它不会做错事**，因为发送前有两道基于屏幕本身的核对。

### 2.2 那个没解决的**风险**（注意用词）

**准确的说法是"风险"，不是"一定会停"。**

Android **不会**在应用一进后台就冻结进程：它先进**缓存进程**，通常还能继续跑；只在**内存压力**下才可能被杀，Android 13+ 的 **Cached Apps Freezer** 才可能真正冻结——**时机不确定，而且从应用内部观测不到**。

所以"一离开循环就停"**不是事实**，是个风险。而**提前中止并不解决它**：无论进程是被冻结还是被我们主动停掉，任务同样没做完。差别只在于前者**没有可见结果**。

### 2.3 后备选项：前台服务（**暂不实现**）

> **状态：已评估，明确推迟。** 这一段是设计备忘，不是已有能力。代码里没有任何前台服务。

这是**唯一能真正消除该风险**的东西：

| 要改 | 内容 |
|---|---|
| `app.config.ts` | `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_DATA_SYNC` 权限，以及 `<service>` 与 `android:foregroundServiceType` 声明 |
| `apps/mobile/android-native/shizuku/` | 一个 `Service` 子类：`startForeground()` + 常驻通知 |
| `native-shizuku.ts` | 暴露 `startRunService` / `stopRunService` |
| `runtime.ts` | 运行开始时起、结束时停（用现有 `keepAwake` 的同一位置即可） |

**为什么它能解决**：前台服务让本应用的进程在**不可见的情况下仍被系统视为活跃**，从而不被冻结——这正是当前缺的那一块。

**为什么推迟（两条都是硬理由）**：

1. **无法在无真机的情况下验证。** 真机行为（Android 14+ 是否允许该类型、通知是否如预期出现、JS 是否真的继续推进、被冻结时 binder 回调还能不能到）在这里**一条都测不了**。写出来只能得到一个**看起来完成、实际未验证**的东西，比不写更糟——因为下一个人会以为它可用。
2. **它会改变 Play 上架的形态。** `dataSync` 类型需要声明用途；仓库当初**故意**没做，理由写在 `app.config.ts` 的注释里（避免为持久化守护进程要求常驻通知）。这是一个**产品/上架决定**，不是技术顺手改。

**方案已经被评估过并记为路线图第 2 项**（`README.md` Roadmap）。

## 三、为这件事已实现的两条机制

### 3.1 运行时保持屏幕常亮

**问题**：Android 在**熄屏时挂起 Activity**。而屏幕正是被自动化的那个东西——熄屏会让任务因为一个和任务本身无关的原因失败，而且是在**两次工具调用之间无声地**发生。

**做法**：一次运行期间给当前 Activity 加 `FLAG_KEEP_SCREEN_ON`（`MobileClawShizukuModule.kt` 的 `keepScreenOn`）。不需要权限，**系统会在应用离开前台时自动释放**——这正好是想要的语义，因为那时屏幕也不再被自动化了。

**引用计数**：两次运行重叠时（一次取消和一条新指令撞上），只在计数归零时才释放，否则第二次运行中途屏幕就会睡。

**失败处理**：拿不到 Activity、或原生模块旧了 → **静默降级**（屏幕不常亮，但任务照跑）。屏幕不常亮是**降级**，不是**失败**。

### 3.2 不可逆那一步的守卫：**核对读数来自哪个 app**

**这是替代了"切后台就中止"的那个守卫**，也是目前唯一真正保护发送的东西。

**做法**：`screen_send_message` 接受 `expectedPackage`，在**打字之前**和**按下之前**各核对一次：`ScreenSnapshot.package`（这次读数来自哪个 app）必须等于调用者指定的那个。

```
refused: the screen is showing com.tencent.mobileqq, not com.tencent.mm,
         so nothing was sent. The intended app is no longer in front.
```

**为什么这比"查我们自己的前台状态"强**：

| | 旧守卫 | 现在的守卫 |
|---|---|---|
| 问的问题 | 我们自己的 app 在前台吗 | **屏幕上的 app 是计划里那个吗** |
| 和任务相关吗 | **无关**（我们本来就该在后面） | **直接相关** |
| 依据 | 我们进程的状态 | **屏幕本身** |
| 能证明什么 | 几乎什么都不能 | 读数**真的来自目标 app** |

**"读不到 ≠ 不一致"**：后端报不出包名时**不拒绝**。因为"报不出"不等于"错了"，按沉默拒绝会让所有这类设备**完全无法发送**——那是拿真实功能换一个不存在的安全。

`screen_type` 也接受 `expectedPackage`，同样的理由：文字是打进**当前持有焦点**的窗口的，而 `input text` 和剪贴板粘贴两条路都不认目标。

## 四、一条指令要调用几次模型

**每一次"step" = 一次模型调用。** 循环在四种情况退出：`completed` / `step_limit` / `cancelled` / `error`。

**步数**：默认 **12**；`confirm_plan` 允许计划声明需要多少步（上限 **60**）。**模型不能自己抬预算。**

### 关键：每一轮都重发完整历史

```js
messages: [{ role: "system", content: system }, ...conversation.messages]
```

所以 **token 成本大约按步数的平方增长**：第 12 步会把前 11 步的模型输出和工具结果全部重发一遍。

**这正是 `catalog` 存在的理由**：工具目录在提示词里**只占一行**（名字 + 一句话），需要精确参数时才去调 `catalog`。否则 35 个工具的完整 schema 要出现在**每一次**调用的系统提示里。

### 一个具体例子

"读微信某人的消息 → 总结 → 发给 QQ 某人"：

| 步 | 动作 | 模型调用 | 需要你点吗 |
|---|---|---|---|
| 1 | 复述计划确认 | 1 | **✋** |
| 2 | `screen_open_item` 打开微信会话 | 2 | **✋** |
| 3 | `screen_read` 读消息 | 3 | 不用 |
| 4 | `screen_scroll` 翻页 | 4 | **✋** |
| 5 | `web_search` 查证 | 5 | 不用 |
| 6 | `screen_read` 定位 QQ 会话 | 6 | 不用 |
| 7 | `screen_open_item` 打开 QQ 会话 | 7 | **✋** |
| 8 | `screen_type` 打字 | 8 | **✋** |
| 9 | `screen_send_message` **发送** | 9 | **✋ 永远要** |
| 10 | 给出最终文字 | 10 | — |

**约 10 次模型调用**，其中 **5 次需要你点确认**。同一会话里重复同类操作后，可减到 **2 次**（计划 + 发送）。

## 五、默认审批策略

`apps/mobile/src/runtime/config.ts`：

| 风险级 | 默认 | 工具 |
|---|---|---|
| **read** | **静默** | `fs_read` `fs_list` `fs_search` **`screen_read`** `screen_find`（只找不点） `system_apps` |
| **network** | **静默** | **`web_search`** **`web_fetch`** **`enrich_list`** |
| write | 问 | `fs_write` `fs_edit` `system_clipboard` |
| execute | **每次必问** | `shell_run` `python_run` `shizuku_request` |
| system | 问 | `screen_capture` `screen_tap` `screen_scroll` `screen_type` `system_share` `system_calendar` |
| —— | **显式拒绝** | `shizuku_run` |

**永远要问、且无法配置关闭的**（`alwaysAsk` + `neverRemember`）：

| 工具 | 为什么不能关 |
|---|---|
| **`screen_send_message`** | **消息发给真人不可撤回** |
| **`confirm_plan`** | 整体意图的闸门 |
| `screen_capture` | 截图是存证，每次都问 |

**发送那一步是硬约束，不是默认值。** 即使把其他都设成静默，"发送"仍然每次都问——这不是"暂时没做自动批准"，而是**这个项目不应该达到的状态**。

## 六、一句话总结

**这是一个"人在场"的自动化，不是无人值守的机器人。**

- 手机屏幕留给被操作的 app，本应用在后台**继续跑**（不会因为你切走就中止）
- 屏幕上的 app 换了 → 发送前的核对**拒绝**，**不会做错事**
- 进程被系统冻结时，任务**停住且不报错** —— 这是目前唯一的真实缺口，解法是前台服务（**已推迟**）
- 每步一次模型调用，且每步重发全史，所以**步数就是钱**
- **发送永远要你点一下**
