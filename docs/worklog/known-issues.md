## 一、后台进程被冻结 → 整个 agent 停住（**当前最关键的问题**）

**来源**：用户 2026-10-11 明确指出两次——"没有后台权限，这个软件放在后台无法正确运行"、"最关键的解决后台无法使用的问题"。

**为什么它排在功能缺口之前**：驱动整个 agent 的是**本进程里的 JS 循环**。进程被系统冻结，循环就停了 —— 不是"走得慢"，也不是"某一步失败"，而是**在两次工具调用之间无声地停住**。此时 §5.1、§5.2、§7.1 那些能力（重置到启动页、页面核对、深链）**一个都用不上，因为根本没有代码在跑**。**后台保活不是一个功能，它是其它所有功能的前提。**

| 项 | 内容 |
|---|---|
| **现象** | 用户 2026-10-11 报告"没有后台权限，这个软件放在后台无法正确运行"。实测现象是：agent 走到"打开网易云"这一步之后**一直停住** |
| **为什么这是结构性的** | 操作别的应用时，**我们必然在后台**（手机一次只显示一个应用）。而 Android 会冻结后台进程，**冻结会停掉整个 agent 循环**——它是 JS，跑在本进程里。`FLAG_KEEP_SCREEN_ON` 只防止熄屏挂起，**不防止进程被冻结** |
| **与 §五 是两个不同成因** | "停住"有两种可能：**进程被冻结**（本条）或**缺导航能力**（§5.1，表现为继续读屏但走不下去）。**区分方法**：回到 app 看对话是否还在推进——冻结则全停，缺能力则继续读屏但无进展。**这个判断必须先做**，否则可能修错方向 |
| **当前状态** | 全仓库搜 `startForeground` / `FOREGROUND_SERVICE` → **0 处**。`docs/runtime-prerequisites.md` §2.3 记为"已评估、明确推迟"，推迟理由有两条：①**无真机无法验证** ②会改变 Play 上架形态（`dataSync` 类型需要声明用途，且要常驻通知）。**理由 ① 现在不成立了**——项目已有可测真机，且 2026-10-11 已用 release 包验证过 `shell_run` |
| **将来怎么接（前台服务）** | 涉及四处：①`app.config.ts` 加 `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_DATA_SYNC` 权限与 `<service android:foregroundServiceType="dataSync">` 声明（**走 config plugin**，对标已有的 `withShizukuManifest`/`withShizukuGradle`，否则 prebuild 会清掉）；②`apps/mobile/android-native/shizuku/` 加一个 `Service` 子类，`startForeground()` + 常驻通知，通知文案走 `ui/strings.ts`；③`native-shizuku.ts` 暴露 `startRunService`/`stopRunService`（**做成可选方法**，旧原生模块不该让整个模块加载失败——这是仓库既有惯例）；④`bootstrap.ts` 用 `AppState` 在 app 变为可见时启动服务 |
| **关键陷阱（会让朴素实现失败）** | Android 12+ **禁止从后台启动前台服务**，抛 `ForegroundServiceStartNotAllowedException`。而"运行开始时起、结束时停"这种朴素做法**正好在需要它的那一刻从后台调用** → 必然失败。**正确做法是服务常驻**：在 app 可见时启动一次，之后一直带着通知运行，运行期间不再启停 |
| **代价（需要产品决定）** | 一个**常驻通知**。这是前台服务的本质——系统要求用户看得见有东西在后台跑。若用户不接受，只剩下面这条替代方案 |
| **未验证的替代方案：悬浮球** | `SYSTEM_ALERT_WINDOW` 理论上也能提高进程重要度、且不需要常驻通知。但有三个问题：①它是**特殊权限**，要用户去"设置 → 应用 → 特殊权限 → 显示在其他应用上层"手工开，那个提示比"有一个通知"更吓人；②**会遮挡屏幕**，与 `screen_read`/`screen_tap` 直接冲突（可能出现在 `uiautomator dump` 里，或盖住 `screen_tap` 的坐标）；③能否真正防冻结**依赖 ROM 省电策略**（尤其国内 ROM），在此无法验证。**另注意**：debug 构建里这个权限来自 **React Native 的 debug manifest**（`node_modules/react-native/ReactAndroid/src/debug/AndroidManifest.xml`），**release 里不存在**，要用必须显式声明 |
| **怎么验证修好了** | 发起一个多步任务，在 agent 打开目标应用后**切到那个应用**，观察任务是否继续推进（而不是回到 app 才发现停住）。修复前是全停；修复后应当继续 |

## 二、语义树读不到的屏幕内容（已知盲区）

**来源**：用户 2026-10-09 明确指示——"如果出现了图片等这种语义树显示不出来的，可以暂时先不用管他，但是要记录到问题日志里"。

### 2.1 图片 / 表情包 / 语音 / 红包 / 转账

| 项 | 内容 |
|---|---|
| **现象** | 无障碍树里这些只有**占位节点**（一个 `ImageView` / 无文字的容器），**没有内容**。`screen_read` 会把它读成一个没有 text/description 的节点，然后被投影层当作"结构性节点"丢掉 |
| **影响** | "读微信聊天内容并整合"这类任务，**只能拿到文字消息**。图片里的信息、语音内容、红包金额一律读不到 |
| **现在为什么不做** | 要拿到这些需要另一条读取通道（OCR 或 `FLAG_SECURE` 级别的权限），成本远大于收益，且用户明确说暂时不管 |
| **将来怎么接** | `AutomationService.readScreen` 已经预留了分层空间：先语义树，失败/缺失再降级 OCR。OCR 接口该挂在同一个端口上，作为 `readScreen` 的**第二个实现**，而不是新增一层工具 |
| **怎么验证修好了** | 构造一个只有图片消息的界面，`screen_read` 能返回图片里的文字 |

### 2.2 读不到的情况下，不要假装读到了

**这一条是纪律，不是缺口**：语义树读不到内容时，**必须如实说明**，不能让模型推测。
现有实现（`ui-dump.ts` 的 `STRUCTURAL_ONLY` / `screen-read.ts` 的 `note` 透传）已经保证"读不到"不会被说成"屏幕是空的"。
**改动这里之前先读 `docs/architecture.md` 的架构不变量第 8 条。**

### 2.3 截图存在应用专属目录里，系统相册看不见

**这是刻意的选择，不是缺口**（来源：用户指示"把 AI 自动截下来的图放到 app 专属路径里，不耽误系统自带的相册"）。

| 项 | 内容 |
|---|---|
| **存在哪** | `filesDir/screenshots/`（`MobileClawShizukuModule.kt` 的 `screenshotDir()`） |
| **为什么不是相册** | 截图里常含**别人的私密聊天**。app 内部目录**永远不会被 MediaStore 索引**，别的应用也读不到，**且不需要任何存储权限**——所以不需要 `MANAGE_EXTERNAL_STORAGE`，Play-safe 构建不受影响 |
| **为什么不是 `cacheDir`** | `cacheDir` **系统会自动清**。证据图某天无声消失，就无法再核对当时屏幕上是什么。`filesDir` 持久，清理**完全由我们负责** |
| **为什么不用工作区目录** | 工作区根是用户**可能指向共享存储**的那个路径（"自定义工作区目录"是很自然的需求）。一旦那样，截图就会进相册。改成固定目的地，这件事就是**决定**而不是**巧合** |
| **代价** | **相册看不见 ⇒ 只有本 app 能看**。所以必须有 `app/screenshots.tsx` 这个浏览页，否则图只写不读 |
| **保留策略** | 默认 **3 天**（可设 1/3/7/30/永久）。**启动时 + 每次截图后**各跑一次（只在退出时跑不行——app 可能被系统杀掉，那就永远不删） |
| **删除的两种规则** | **过期自动删：不确认**（一个没人执行的保留期不叫策略；对定时删除弹确认会训练用户无脑点过）。**手动删：必须确认**（是"agent 对别人会话做了什么"的证据，误删不可撤销） |
| **边界处理** | 时间戳读不到的图**当作新的**（保留）；保留期设成无效值也**当作保留**。两个都朝"保留"这个方向失败——多留几 KB 可以再删，删掉的证据没有任何按钮能恢复 |
| **怎么验证的** | `apps/mobile/test/screenshots.test.ts` 13 个用例，钉住**边界**（正好 3 天保留、刚过 1 毫秒删除、无时间戳保留、无效设置保留）和**一个文件删不掉时继续扫**。`capabilities.test.ts` 另有 4 个用例钉住"进专属目录不进工作区""没配目录时交给后端""清理后报告张数" |
| **未验证** | **真机**：`filesDir` 路径、缩略图能否渲染、`Alert` 确认框的实际表现。模拟器与真机行为不同 |

## 三、step 预算会超的复杂任务

**来源**：同一次指示——"爆预算这个问题也先不用管，写在日志里"。

| 项 | 内容 |
|---|---|
| **现象** | `Agent` 默认 `maxSteps = 12`（`packages/core/src/agent.ts:118`）。"打开 A → 读 → 滚屏 N 次 → 打开 B → 搜人 → 输入 → 发送 → 回读核对"这种跨应用任务**必然超预算** |
| **量化** | 一个"读微信并转发给 QQ 某人"任务顺利情况下约 11–16 步。滚屏读长聊天时，**每滚一次 0.6 屏就占 1 步**，读 100 条历史消息要十几步 |
| **影响** | 任务跑到一半停住，报"Stopped at the step limit"，用户看到的是未完成状态 |
| **现在为什么不做** | 用户明确说先不管；而且真正的解法不是调大数字，而是减少步数 |
| **将来怎么接**（按优先级） | ① 把"取 A 写 B"做成**一个专用工具**在内部跑完整条流水线（一次调用 = 一步，而不是十几步）；② 让 `screen_read` 支持一次读多屏 / 返回可滚动容器的全部子节点；③ 最后才是调大 `maxSteps` |
| **怎么验证修好了** | 用脚本化 provider 跑一个 20 步的跨应用任务，能在默认预算内完成 |

## 四、把信息真正"发出去" —— ✅ **全部解决**

> 这一节原来的两条缺口都已实现。**"我做了什么"从此由代码产出，而不是由模型描述。**

### 4.1 收件人核对 —— ✅ `screen_open_item`

| 项 | 内容 |
|---|---|
| **原来是什么问题** | 在 B 应用里搜昵称会返回**多个相似结果**；`screen_find` 按"最短标签优先 + 可点优先"选一个，**可能选错人**。然后一按发送，消息就发给了错误的人 |
| **为什么最严重** | **不可撤销的真实后果** |
| **做法** | `packages/capabilities/src/tools/screen-open.ts`，三条规则：<br>① **拒绝在候选之间选择**——多个**不同**标签都能匹配就**不猜**，返回候选清单让用户选；<br>② **`expect` 必填**——点完**读回屏幕**断言目标文本在，失败返回 `unverified`；<br>③ **已经打开就不点**（在已打开的会话里点同一个名字会开资料页或另开会话） |
| **关键设计** | 刻意**不带 `mutates: false`**，所以**只读任务作用域不能让它静默**——它能以"消息发给了某个人"结束 |
| **怎么验证的** | `screen-open.test.ts`，12 个用例，其中**互相镜像的两条**最关键：<br>· 不可点的同名节点是**标题**（已打开）→ 不重复点击；<br>· 不可点的同名节点是**没按下去的结果行** → 必须报 `not-pressable`，**不能谎称已打开**。<br>这两种读法在无障碍树里长得一样，区分它们才是难点 |

### 4.2 发送动作本身 —— ✅ `screen_send_message`（原子发送）

| 项 | 内容 |
|---|---|
| **原来是什么问题** | 就算打开了正确会话，**发送那一刻**屏幕可能已经变了。用 `screen_type` + `screen_find` 按"发送"拼出来的序列，**每一步都能在错误的屏幕上成功**——而没有任何单独一步能察觉，因为它只知道自己那一瞬间的屏幕 |
| **注意**：3.1 的核对发生在**打开那一刻**，而模型之后可能又按了几个键、翻了几页。**严格说，发送前的标题核对才是最后一道闸** |
| **做法** | `packages/capabilities/src/tools/screen-send.ts`：一次**原子**动作，四步每次重读屏幕，**任何一步存疑就一个键都不按**：<br>① 目标会话**是不是当前页**（要求"不可点的、精确等于目标"的节点存在）；<br>② 发消息就**打字 → 等一次布局 → 确认文字真的在**；<br>③ 内容核对：会话上必须能看到 `expect`（证明这条消息属于这个会话）；<br>④ **发送前最后一读只核对收件人，紧接着就是按下** |
| **顺序为什么这么排** | "已核对"到"已按下"之间的间隙，是唯一可能发错人的窗口。所有其它工作（打字、确认文字、内容核对）**都排在这最后一读之前**，所以慢应用或布局变化**不可能在两个检查之间把收件人换掉** |
| **`sendLabel` 为什么必填** | 猜哪个控件是发送按钮，就是按错按钮的方式。找不到就拒绝，并把"请给出用户看到的发送按钮文字"作为指引返回 |
| **多处匹配也拒绝** | 有两个不同控件都应答"发送"时按其中一个**就是猜**，而猜的结果落在一个有真人的会话里 |
| **最强的权限姿态** | `risk: system` + `alwaysAsk` + `neverRemember`，而且**不带 `mutates: false`**——三重都承重：白名单、会话级"总是允许"、只读任务作用域**都不能**让它不问就按 |
| **怎么验证的** | `screen-send.test.ts`，13 个用例。最关键是**竞态那条**，而且它的**编排必须精确**：内容核对要**通过**（否则跑不到最后一读），只有最后一次读数不同。**我第一版把这个变化放在第三次读数上，被内容核对提前拦住了——于是被保护的守卫根本没被走到，撤掉它测试照样通过。** 变异检查抓到了这一点，现在撤掉那一读 → 竞态测试失败 |
| **顺带** | 返回 `nothingWasSent: true` 与"不要原样重试"，避免模型把拒绝读成软失败 |

### 4.3 写入后的回读核对 —— ✅ `screen_type` 的 `expect`

| 项 | 内容 |
|---|---|
| **原来是什么问题** | `screen_type` 打完字就返回 `{method, length}`，**没有一步确认文字真的进了输入框**。只读字段、被拒绝的粘贴、失去焦点的输入框三者看起来和成功一样 |
| **做法** | `screen_type` 新增可选参数 `expect`：**写 → 等 350ms → 读回屏 → 断言**。返回 `{verified, verifyNote}`，失败时措辞含 `do not report this as done`。**报告而不抛异常**（写入已发生，抛异常会诱导重试），也**不自动执行**（核对要多一次读屏） |
| **怎么验证的** | `capabilities.test.ts` 里 5 个用例，其中一个用**读取计数器**证明不传 `expect` 时**完全不读屏** |

## 五、"读歌单"这类任务走不下去

**来源**：用户实测——"我让他去看我网易云都有什么歌单（需要先打开网易云，再打开个人界面，再读），但实际上他走到打开网易云这一步之后就一直停住了"。

**这一节的两条是同一现象的两个成因，且都不是"权限不够"。** 打开应用本身已经可用（`2026-10-11` 实测：`system_open(packageId)` 弹出系统确认框 → 允许 → 直接跳到网易云，不是之前那个候选列表）。真正缺的是下面两条。

### 5.1 没有"把应用弄回已知状态"的能力

| 项 | 内容 |
|---|---|
| **现象** | 同一个应用，**当前处在什么状态决定了下一步该怎么做**：没打开过 → 直接打开并落在首页；**已经打开且停在深层页**（网易云会恢复上次位置）→ 得先一步步退回首页，或把它重置。而仓库里**没有任何导航类能力**：全仓库搜 `force-stop` / `monkey` / `keyevent` / 返回键 → **0 处** |
| **影响** | 模型打开应用后发现自己面对的页面和预期不符，**手上没有任何工具可以改变这一点**（只有 `screen_scroll` / `screen_tap` / `screen_type`）。它的表现就是**反复读屏然后停住** —— 与用户看到的现象一致。这也让 `system_open` 的结果不可预测：同一个调用有时落在首页、有时落在上次的深页 |
| **现在为什么不做** | 需要先定权限姿态（`am force-stop` 会**杀掉**应用，可能有未保存内容），且依赖 Shizuku（已验证可用：uid 2000 的 `am start` 在用户设备上工作正常） |
| **将来怎么接** | 加一个"重置到启动页"工具，**不要**做"一步步退回"——后者要求模型知道层级有多深，很脆，且应用状态一变就失效。可靠形式是 `am force-stop <pkg>` 然后 `am start -n <component>`：**一条命令、状态确定、可核对**（用 `currentWindow().activity` 确认落到了启动页）。实现位置对标 `packages/capabilities/src/launching.ts`（该文件曾写过特权 `am start`，因当时判断不需要而搁置；`stash@{0}` 里还有一版，但它做的是"打开"而非"重置"）。**包名必须走 stdin，不能拼进命令**（模型给的值不可信，`com.x; rm -rf /` 是合法包名字符串） |
| **权限姿态待定** | 按用户定的原则「只有发送这种必须做更改或删除的才必须审批」，`force-stop` **算不算"更改"**需要用户确认。它确实会改变设备状态（杀进程），倾向需要审批 |
| **怎么验证修好了** | 把网易云手动翻到某个深层页，然后让 agent 执行"看我的歌单"——它应当先重置到启动页，且 `currentWindow().activity` 报出的是启动页而非上次的深层页 |

### 5.2 `system_open` 不核对"是否真的到了"，也不报"到了哪一页" —— ✅ **已实现，真机未验证**

> 2026-10-11 实现。下面保留原始分析，改动的说明在末尾。

| 项 | 内容 |
|---|---|
| **现象** | `packages/capabilities/src/tools/system.ts` 的 `execute` 结尾是 `return { ok: true, opened: input.url ?? input.packageId }`。包名那条会先 `await deps.system.openApp(...)`，**失败会抛异常并传播**（这一点 0.3.1 已经修好，不再是"假成功"）；但**成功路径没有任何核对**——它不知道应用有没有真的到前台，也不知道落到了哪一页 |
| **影响** | 模型拿到 `ok: true` 却无法验证，于是**只能靠读屏猜自己到没到**。而"到了哪一页"恰恰是决定下一步的关键信息（见 5.1）。这也是提示词里那条"公开接口优先、读屏兜底"策略缺的一环：有兜底，但**没有反馈说该不该兜底** |
| **将来怎么接** | `ForegroundWindow` 类型里**已经有 `activity` 字段**，由 `parseForeground` 从 dumpsys 解析出来，`screen_current` 已经把它摊开返回。做法：`system_open` 在打开后轮询 `currentWindow()`，把 `package` + `activity` 一并返回；**读不到时如实报 `unverified`，不能报成功也不能报失败**（"读不到" ≠ "没打开"，这是仓库的架构不变量）。可复用 0.3.3 新增的多来源回退 |
| **怎么验证修好了** | 在"读不到前台"的设备上调用，返回值是 `unverified` 且带 `raw`；在正常设备上，返回值里的 `activity` 与实际落地页一致 |

**已实现的方式**（`packages/capabilities/src/app-state.ts`）：

- `awaitArrival(packageId, readForeground, options, ctx)` 轮询前台（默认 250 ms 间隔、5 s 上限），返回三态：`arrived` / `not-foreground`（**读到了，但是别的应用**）/ `unverified`（**读不到**）。
- **"读不到"永远不是"没打开"**：只有 `not-foreground` 是"启动没落地"的证据。这一条单独有两个测试钉住，并做过变异验证（把 `unverified` 改成 `not-foreground` → 2 个测试失败）。
- **报出 `activity` 是重点**：微信和网易云都会恢复上次停留的界面，所以"打开了应用"和"落在首页"是两个不同的事实。
- `readForeground` 默认取 `system.automation.currentWindow()`——**和 `screen_current` 用同一个探针**，所以"到了没到"由模型本来就会手动去问的那个读数回答，不引入第二套判据。
- 新增 `settleMs` 参数：在**读不到前台的设备**上，否则每次打开都要付满 5 s。有测试证明它生效（`settleMs: 0` 时调用 < 1 s 返回）。

**未验证**：真机上 `activity` 的实际取值与落地页是否一致、`unverified` 路径在真实 ROM 上的表现。

## 六、启动应用是否算"更改"（审批模型，待随实现确认）

**来源**：用户 2026-10-09 定的审批原则——"打开和读的不需要审批，只有发送这种必须做更改或删除的才必须审批"。

| 项 | 内容 |
|---|---|
| **现状** | `system_open` 目前是 `risk: "system"`，会弹审批；`screen_tap_element` / `screen_find(do:"tap")` / `screen_type` 是 `neverRemember`，每次弹 |
| **问题** | 按新原则，"打开应用""读歌单"都不该审批。但 `screen_find(do:"tap")` 这类**中间点击**难以静态判断是"读"还是"改"——在设置页点一下是读，在聊天页点"发送"是改 |
| **待定** | 需要确定：是①按工具粗粒度放行（打开/读取类免审批），还是②把审批**收敛到任务级**（用户确认一次任务复述，之后中间步骤不再打断），只在不可逆动作（发送/删除）前再确认一次 |
| **倾向** | ②。因为逐次弹窗会训练用户盲点"同意"，反而降低安全性——这一点在 `prd` 里也记过（"批量操作＝一次逻辑确认，不是逐文件弹窗"） |
| **怎么验证修好了** | 一个"读歌单找关键词"任务全程零审批弹窗；一个"发送消息"任务在发送前恰好一次确认 |

## 七、已确认并已接入的能力

### 7.1 网易云注册了自定义 deep link（`orpheus://`）—— ✅ **已接入 `system_open`，真机未验证**

**来源**：2026-10-11 真机实测，`dumpsys package com.netease.cloudmusic` 列出的 scheme。

| 项 | 内容 |
|---|---|
| **事实** | 网易云注册了 `orpheus`、`apporpheus`、`cloudmusicopenapi` 等自有 scheme（另有 `http`/`https`/`content`/`file` 这些通用项，以及一批支付/登录回调 scheme）。实测 `am start -a android.intent.action.VIEW -d "orpheus://"` 可用 |
| **为什么重要** | 这是**导航脆弱性**（5.1 的另一面）的解药之一：深链直接跳到目标页，**不关心应用当前在哪一页**，因此天然绕开"已经打开过就要退回首页"这个难题。而且提示词里的策略阶梯**早就把深链排在第 2 位**（直接工具 → 深链 → 读屏 → 坐标），但当时只能承认"when the app documents one"，因为不知道任何应用的实际 scheme |
| **未确认的** | ① 能否直达**歌单页/个人页**（需要 `orpheus://` 的 host/path 模式，即 `dumpsys` 里对应的 `Authority:`/`Path:` 声明，尚未查）；② **是否弹确认框**（从 uid 2000 出发理论上不受"后台启动 Activity"限制，但"打开支持的链接"确认是另一套机制）；③ 对没有自定义 scheme 的应用不适用 |
| **怎么验证** | 让 agent 执行"看我的歌单"，它用深链直达歌单页，且返回值里的 `activity` 与手工点进去的一致 |

**已接入的方式**：

- `system_open` 新增 `deepLink` 参数（与 `packageId`、`url` **三选一**，给两个就拒绝——两个互相矛盾的目标哪个都不是能猜的）。
- 自定义 scheme **走特权 shell**（`packages/capabilities/src/deep-link.ts` 的 `deepLinkCommand()`），`am start -a android.intent.action.VIEW -d`。**不走 `openUrl`**，因为 `openUrl` 经普通 launcher 解析，自定义 scheme 会让 Android 弹"打开方式"确认框——而 run 期间我们在后台，那个框画在没人看的屏幕上，任务就卡在它后面。
- **URL 走 stdin，绝不拼进命令行**。URL 是模型给的，`am start -d "$url"` 会让一个引号或 `;` 把"打开链接"变成"执行别的命令"。有测试断言 **URL 完全不出现在命令里**（不是"被转义了"，而是根本不出现）。
- `am` **把失败写在 stdout 且仍然退出 0**，所以判据是文本不是退出码。`no-handler` 单独成一种结果（而不是"失败的变体"），因为那是模型能据此行动的事实：换个链接或问用户，而不是重试。
- **深链不声称核对过落在哪个应用**——scheme 由谁处理在事实发生前不可知，返回值明说 `verified: "not-checked"`。把一个未核对的结论包装成已核对，正是这个项目禁止的事。
- **深链不能替代"重置到启动页"**（5.1）：前者只对提供深链的应用有效，后者对所有应用有效。两者应并存：重置保底，深链在可用时更快。

### 7.2 `shizuku_run` 曾被默认规则永久禁用（已移除）

| 项 | 内容 |
|---|---|
| **现象** | `apps/mobile/src/runtime/config.ts` 的 `DEFAULT_PERMISSIONS.rules` 里有一条 `{ tool: "shizuku_run", decision: "deny" }`，模型调用时收到 `[E_PERMISSION_DENIED] denied by rule for "shizuku_run"`。用户 2026-10-11 撞上它：想用 `shizuku_run` 查一个应用的 deep link scheme 被拒，而 `shell_run` 同时因为另一个 bug 不可用，于是无路可走 |
| **那条规则的注释是错的** | 注释写的是"Never let the model delete outside the sandbox silently; the organize tool already forces a prompt"。但仓库里**没有**这类删除工具（`fs_organize` 是唯一有牙齿的文件系统工具，且自带 `alwaysAsk`）。注释描述的对象不存在 |
| **为什么它没增加安全性** | `shizuku_run` 自带 `alwaysAsk: true` 且 `risk: "system"`，而 `system` 映射到 `ask`，所以它**本来就不可能静默执行**；同时 `shell_run` 经 `pickShellBackend` 到达**同一个**特权 shell 且从未被禁。想跑命令的人不需要 `shizuku_run` |
| **代价** | 挡住了需要 shell 身份的**只读**诊断（`dumpsys package` 枚举 scheme 就是典型），而那正是这个工具存在的意义 |
| **已做** | 规则改为 `rules: []`，并把上述推理写进注释 |

### 8.7 shell 后端只在启动时判定一次，且吞掉真实原因（已修）

| 项 | 内容 |
|---|---|
| **现象** | `shell_run` 一直回答「no shell backend: install Termux (or pair Shizuku)」，而同一时刻 `shizuku_status` 说 Shizuku **可用**。两个答案回答同一个问题，用户看到的是错的那个 |
| **根因** | `pickShellBackend` 里 `if (await privileged.isAvailable()) return new NativeBridgeShell(...)`。Shizuku 的 binder 在应用刚起来那几秒经常还没应答 → 判断为假 → 落到 Termux 分支 → **结果在整个进程生命周期内被固化**。而 `NativeBridgeShell.available()` 本来就是**每次调用时**才问的，所以启动时探活唯一做到的事就是**决定得太早、然后一直说假话** |
| **叠加缺陷** | 那个 `try/catch` 是**空 catch**，把 Shizuku 未运行 / 权限没给 / binder 挂了 / 原生模块不在**四种完全不同的情况**归成同一句"你没装 Termux" |
| **已做** | 抽出并导出纯函数 `selectShellKind({ hasPrivileged, termuxInstalled })`，按**种类**选而非按探活选；空 `catch` 随之消失；无后端文案改为事实。新增 `apps/mobile/test/shell-backend.test.ts`（5 例），**已做变异验证**：把实现改回"有模块却返回 memory"，3 例失败 |
| **真机验证** | 2026-10-11 release 包：`shell_run` 执行 `dumpsys window \| head -n 2` 返回**退出码 0 且有 stdout**；修复前这里只返回「no shell backend」 |


## 九、记录格式约定

新增一条时请包含：**现象**（可复现的事实）、**影响**（对产品/用户意味着什么）、**现在为什么不做**、**将来怎么接**（具体到文件/端口/函数）、**怎么验证修好了**（一个能失败的测试长什么样）。

没有"将来怎么接"和"怎么验证"的条目，等于把问题丢给下一个人重新发现一遍。
