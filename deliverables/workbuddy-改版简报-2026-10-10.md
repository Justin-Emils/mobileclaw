## 1. 产品重新定义（一句话）

> **MobileClaw 是一个住在手机里、能穿行在各个 App 之间的助手 —— 把散落在不同 App 里的信息收拢到一起，把一件事编排到多个 App 上完成。**

不是"文件整理工具"，也不只是"说一句话办事"。区分标准不是"它能不能干活"，而是**"它能不能把两个本来不相干的 App 连起来"**。

立项时的原始意图一直写在 `README.md` 第 4 行：`it gets real hands (files, shell, scripts, cross-app actions)` —— "cross-app actions" 是原话。请以它为准。

**五种"连接"模式**（比功能清单更能指导设计）：

| 模式 | 说的是 | 例子 |
|---|---|---|
| 收拢 | 把散在 N 个 App 里的东西汇到一处 | "今天所有 App 里有什么事找我" |
| 搬运 | A 的东西加工后进 B | 浏览器看到一段 → 总结 → 存进笔记；地址 → 存联系人 → 导航 |
| 编排 | 一句话触发跨多个 App 的一串动作 | "我下周三去上海" → 建日程 + 查车票 + 存地址 + 设提醒 |
| 代理 | 替你进某个 App 里操作 | 自动发微信、自动点外卖 |
| 理解 | 不连 App，连它背后的服务 | 某个 App 只是壳，数据真正的来源是它背后的服务 API |

**大部分爽感在"收拢"和"编排"，而这两个基本都在合法通道里。**"代理"是最贵的一层：**模式要保留（不许删），但它不进主包承诺**，见 §5.4。

## 2. 安卓能力的真实分层（这是实测数据，不是判断）

我（用户侧）已经在真机上采集完毕，材料见 §6。核心结论：

### 2.1 能力分三层

| 层 | 机制 | 能干什么 | 能不能枚举 |
|---|---|---|---|
| 门 | Activity/Service 的 intent-filter | 让别的 App「跳进来」 | ✅ 可枚举 |
| 数据 | ContentProvider | 让别的 App「把数据取出来」 | ✅ 可枚举 |
| 参数 | 深链的 host 与路径 | 跳进去之后带什么 | ✅ 可从 `dumpsys package` 解析 |

### 2.2 实测数字（小米 2509FPN0BC / Android 16 / SDK 36）

- **能力矩阵**：234 个 App × 28 项能力（可被调用）。28 项里含"接收分享·文字/图片/视频/任意文件/多个文件"（来自 `ACTION_SEND` / `ACTION_SEND_MULTIPLE` 探测）、"处理选中文字"（`ACTION_PROCESS_TEXT`）、"发短信/发邮件"（`ACTION_SENDTO`）、以及建日程/建联系人/扫码/导航等。
- **数据接口**：共 713 个，实测 183 个，完整分布如下（**七类相加 = 183，一项不漏**）：

  | 实测结果 | 数量 | 含义 |
  |---|---|---|
  | 可读 | **12** | 第三方能读到，且**有数据** |
  | 可读·无数据 | 23 | 能读，但实测为空 |
  | 需要权限 | 47 | 接口存在，但要签名级权限（拿不到） |
  | 未导出（第三方读不到） | 88 | 直接锁死 |
  | URI 不存在 | 4 | 探测目标无效 |
  | 无响应 | 3 | 有声明但不响应 |
  | 其它 | 6 | 未归类 |

  > 注意：**"可读 12" ≠ "其余 171 都不可读"**。真正"不是为第三方准备的"是 47+88=135 那部分。写成三项相加会是 147，那 36 条就被吞掉了——上次的写法就是这么错的。
- **深链**：声明 7084 条 → 去重后 6639 条入全量表 → 聚合成 **281 个协议**。其中 **188 个（67%）** 的用途依据是"App 自己声明的组件类名"（不是推测）；另 93 个是通用分发器，只能靠路径关键词猜，**需要实测**。
- **媒体库服务**：18 个 App 开放了可被浏览的媒体库（MediaBrowserService）。（原始 CSV 里有 3 条只填了包名、App 名为空。）

### 2.3 一条必须写进文档的规律

> **能"跳进去"的（深链/Intent）大多开着；能"把数据取出来"的（Provider）大多锁着。**

安卓的设计哲学就是 App 之间不许互读数据。实测证据：

- **微信的能力清单只有 5 项，且全部是"接收分享·文字/图片/视频/任意文件/多个文件"** —— 它能把东西**接进去**，没有任何一项是"发出去"。所以"让微信替你发消息"不是难，是**它根本没声明这个门**。
- 微信**有** `ShareableChatRecords`（可分享聊天记录），但要 `com.tencent.mm.app.provider.ShareableChatRecords.READ_BY_CONSENT` —— 注意它写在"需要权限"那一类里。
- QQ 的 `qq.friendlist`（好友列表）直接是 **not exported**。

**"接口存在" ≠ "你能用"。** 请不要再写"通过读取其他 App 数据实现 X"这类需求。

### 2.4 通道分级（请用它替换旧的"上架/不上架"二分法）

| 级别 | 通道 | 代价 |
|---|---|---|
| 1 | 服务层（API / 网页） | 无，最稳 |
| 2 | 官方 Intent / 分享 / 深链 | 无，能上架 |
| 3 | 剪贴板 | 无，但需用户手动粘 |
| 4 | 通知监听（官方权限） | 低，能上架 |
| 5 | 无障碍（模拟点屏幕） | 封号、上不了架 |
| 6 | Shizuku | 侧载，每次重启要重新授权 |

**产品做得好不好，就看它能不能尽量待在 1–4 层，只在必要时下到 5–6。**
