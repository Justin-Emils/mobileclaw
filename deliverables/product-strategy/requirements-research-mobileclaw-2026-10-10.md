## 📌 TL;DR（3-5 行）

- **定位重写**：MobileClaw 的价值判据从"能不能干活"改为"**能不能把两个本来不相干的 App 连起来**"。五种连接模式——收拢 / 搬运 / 编排 / 代理 / 理解——其中**收拢与编排的爽感最大且基本落在合法通道（1–4 层）内**。
- **需求侧证据**：期望"跨 App 一句话执行"67.8%（中国）vs 真在用手机 AI Agent 仅 14%，缺口显著；中间层 TAM 全球 Android 12+ ≈ 24 亿，SAM 愿侧载 2,000 万–5,000 万，SOM 10 万–100 万（✅ 数析）。
- **能力侧硬事实**：234 个 App 中仅 89 个至少能对外干一件事；覆盖面最广的是"**接收分享**"家族（同一 `ACTION_SEND(_MULTIPLE)` 门）；"**发出去/代理**"类门 ≈ 0（微信 5 项能力全是"接收分享"）——所以**代理必须是进阶包，不进主包承诺**。
- **第一步建议方向（待用户拍板）**：在合法通道内先立"**根基四件套**"——能力发现（工具箱）、分享进→对话、选中文字菜单、深链执行（详见 §7 / §9.2 / §10）。
- **纪律红线**：不删任何能力项；不引入未经拍板的一等约束；不承诺"读取其他 App 数据 / 让微信发消息·读聊天记录"进主包；不把"上架"当产品价值。

## 1. 产品目标

**总目标（新定位补充一句）**：让 MobileClaw 成为**手机里唯一一个能"跨 App 连接"的助手**——把散落在不同 App 的信息**收拢**到一起，把一件事**编排**到多个 App 上完成，并且**每一次连接都可见、可拒绝、可回看、可携带**。

三条长期目标（沿用旧 PRD，继续有效）：

| # | 目标 | 说明 | 关键指标锚点 |
|---|---|---|---|
| **G1** | **零门槛** | 让不会写宏/开终端的中间层用户，在**不进入任何系统设置**的前提下，一句话完成一次真实的跨 App 动作 | 首次价值达成率 ≥50%；首值时延 <90s；解析成功率 ≥90% |
| **G2** | **可信可控** | 把 Agent 的每一次动作变成**可见、可拒绝、可回看**的授权事件 | 任务成功率 ≥85%；审批超时率 <5%；**数据损失事件数 = 0（硬约束）** |
| **G3** | **可移植** | 同一套内核与用户的技能/记忆**跨设备携带**，反厂商锁定 | 模型可换使用率 ≥10%；端侧启用率 ≥5%；换机迁移成功率 ≥90% |

**North Star（建议调整后）**：7 日内**无提示**主动发起 ≥2 次动作的用户 / 周活用户（自发复用率）。跨 App 定位下，新增校验指标见 §5.6「指标建议」。

> **证据纪律（本次新增前提）**：任何"因为政策 X 所以不做 Y"的结论，**必须同时给出"若不考虑 X，Y 是否成立"**。分发（上架）是**待拍板项**，不是一等约束。

## 2. 用户故事（跨 App 场景，覆盖收拢 / 搬运 / 编排；保留 J8 文件动作）

| # | 模式 | 故事：作为〈谁〉，我要〈什么〉，以便〈价值〉 | 主流程 | 成功判定 | 失败/边界 | 通道 |
|---|---|---|---|---|---|---|
| **US-C1** | 收拢 | 作为忙碌的知识工作者，我要**一句话看到"今天所有 App 里谁找我"**，以便不漏事 | 对话输入"今天谁找过我" → 枚举本机可收拢来源 → 汇总 → 逐条可跳转原 App | 汇总条目来自**真实存在的来源**，每条可溯源 | 图片/语音/红包读不到 → 必须如实标注"该来源不可读"，不伪造 | 2 + 4 |
| **US-C2** | 搬运 | 作为爱做笔记的人，我要**把浏览器/聊天里看到的一段文字→总结→存进笔记**，以便沉淀 | 选中文字（`ACTION_PROCESS_TEXT`）或分享进 → 落到对话继续 → 总结 → 写入笔记 App | 笔记里出现正确内容 | 目标 App 不支持写入 → 回退 Share sheet，不静默失败 | 2 |
| **US-C3** | 编排 | 作为常出差的人，我要**"下周三去上海"→建日程+查车票+存地址+设提醒**，以便一次搞完 | 对话一句话 → `confirm_plan` 复述 → 逐 App 深链执行 → 结果清单 | 每个子动作有结果、失败可单独重试 | 默认 `maxSteps=12`，跨应用任务约 11–16 步**必然超预算** → 需预算机制（REQ-06） | 2 |
| **US-C4** | 搬运 | 作为收到地址/电话的人，我要**地址→存联系人→导航**，以便当场出发 | 分享文本 → 解析 → 预览 → 写联系人（系统标准数据）→ 深链导航 | 联系人正确、导航打开正确目的地 | 时间/地点歧义 → 预览高亮待确认；无权限 → 引导授权，不静默丢 | 2 + 系统 API |
| **US-C5（J8 保留）** | 搬运/编排 | 作为临时收文件的人，我要**一句话批量重命名/归档**，以便不逐个改 | 分享多选 → 落到对话 → 输指令 → 预览 → 一次确认 → 通知 | 预览 = 实际结果，可回滚；**绝不静默覆盖** | 200 文件性能；重名冲突加序号/跳过 | 2（SAF tier2 需先见价值） |
| **US-C6** | 代理（进阶包，不承诺主包） | 作为愿意侧载的极客，我要**替我进某 App 点/发**，以便完成无 API 的封闭操作 | 侧载 + Shizuku → 任务复述 → **发送前收件人核对** → 执行 → **写入后回读核对** | 发错人可拦截；陈述由代码从事实生成 | 微信封号/不可上架/重启需重授权；**明确代价后由用户自选** | 5–6 |

> US-C1–C5 属**阶段 1（合法通道）**；US-C6 属**阶段 2 侧载进阶包**（模式保留、不进主包承诺）。

## 3. 用户研究洞察（来自瑞思）

### 3.1 人群分层

| 层级 | 人群 | 规模 | 特征 |
|---|---|---|---|
| **核心** | 独立开发者（BYOK）/ 隐私敏感者 / 效率控 / 极客 | 极客池天花板 **1,000 万–3,000 万** | 愿侧载、要可换模型、要审计 |
| **中间层（大盘）** | 想自动化但**不会写宏/开终端**者 | TAM 全球 Android12+ ≈ 24 亿；SAM 愿侧载 **2,000 万–5,000 万**；SOM **10 万–100 万** | 要"一句话"，怕设置摩擦 |
| **需求缺口** | 期望"跨 App 一句话执行" **67.8%**（中国） vs 真在用手机 AI Agent **仅 14%** | — | 愿望与现状之间是空位 |

### 3.2 两条筛选轴（正交，缺一不迁移）

1. **模型可换**（BYOK，反厂商锁定）；
2. **数据不出机**（local-first 隐私硬约束）。
> 🔶 判断：两条轴同时满足才构成"迁移驱动"，只满足一条不足以让人换工具（待用 5–8 名用户验证，见 3.7）。

### 3.4 跨 App 场景痛点（8 条）

1. 收拢"谁找我"可用，但**图片/语音/红包读不到**（语义树只有占位节点）；
2. `ACTION_PROCESS_TEXT` 真机**已有 12 个 App 注册**（可用的入口已存在）；
3. 一句话多 App 编排可行，但**默认 `maxSteps=12` 必然超预算**（跨应用任务 11–16 步）；
4. 代理=发微信**极难**——微信 5 项能力全是"接收分享"，**没有"发出去"的门**；
5. 代理=读聊天**只能拿文字**，且**发错人不可撤销**；
6. "**跳进去的多开着、取出来的多锁着**"（能跳的门开着，能取的数据锁着）；
7. 中间层对 **SAF 授权摩擦**容忍度待验；
8. 哪些 App 属"**理解**"模式，需逐个实测。

### 3.5 现有替代方案的不满

| 替代 | 不满 |
|---|---|
| Tasker | 需自建宏，**无 LLM** |
| OpenClaw | 需常连 Gateway |
| ChatGPT / Claude | **只读不落地** |
| 厂商内置（小爱/小V） | 能平替文件动作，但**锁死自家模型**、无 BYOK/审计 |
| Operit / PokeClaw | 模型可换，但**只能侧载**、微信严重封号 |

### 3.6 证据否决项（哪些**不能承诺**）

- 主包承诺"**读取其他 App 的数据**"；
- 主包承诺"**让微信发消息 / 读聊天记录**"；
- 分享结果"**原地改好回原 App**"；
- **无障碍当"主路径"**（→ 归侧载进阶包，**不删除**）；
- "**读不到 = 没有**"。

### 3.7 待验证假设（建议 5–8 名用户）

1. SAF 授权摩擦容忍度；
2. "收拢"是否真需求；
3. 跨 App 编排的"爽感"强度；
4. 深链可靠性的**用户感知**；
5. "分享进→落到对话"入口是否自然；
6. 预览 + **一次逻辑确认**能否缓解确认疲劳；
7. 代理模式在侧载用户中的**封号风险意愿**；
8. 模型可换 / 数据不出机是否是**真实迁移驱动**。

## 4. 竞品对比（来自竞析）

### 4.1 五层全景

| 层 | 代表 | 路线 | 短板 |
|---|---|---|---|

### 4.3 可借鉴（6 条）

1. **深链协议表 = 跨 App"动词表"**（6639→281 协议，188/67% 有依据）喂给模型当工具箱，是"**编排**"最低成本实现；
2. **AI Edge Gallery Mobile Actions**：270M FunctionGemma 端侧 function-calling，微调后 **58%→85%**（→ 端侧窄域路由可行性依据）；
3. **MacroDroid「File Shared」触发器**：收来源包名做上下文；
4. **OpenClaw 敏感命令默认关 + 逐项 allowlist + 手机批准**；
5. **Operit 权限分级**；
6. **Shizuku 读树免无障碍**（本仓库已实现）——读取通道可待在**通道 6** 而不用**通道 5**。

### 4.4 必须规避（6 条）

1. **把无障碍当代理主路径** —— Operit 明示"微信会扫描无障碍、**严重封号**"；
2. 承诺"读取其他 App 数据"（183 接口仅 **12** 可读）；
3. 承诺"**原地改好回原 App**"；
4. **逐条确认 → 确认疲劳**；
5. **高权即执行 / 幻觉落地**（发送前不核对收件人=不可撤销；写入后不回读=假装做到）；
6. **全盘 / root / Shizuku 当默认**。

### 4.5 差异化空位（3 个）

1. **合法通道（1–4）内的跨 App 连接**——目前无人占据；
2. **"连接可审计"是一等公民**（可回看的 diff / 决策 / 风险分级）；
3. **连接动作可携带 / 可移植**（Skill 包、换机不归零）。
> **不打**"能连 App 数 / 文件覆盖"军备竞赛。

> **通道表述纪律**：无障碍（通道 5）、Shizuku（通道 6）**不是否决项**，是"**侧载进阶包**"，代价明确写：封号 + 不可上架 + 每次重启重授权。

## 5. 数据依据（来自数析）

### 5.1 实测容量（小米 2509FPN0BC / Android 16 / SDK 36；234 App × 28 能力）

**结论：234 个 App 中仅 89 个至少能对外干一件事。**

| 覆盖档 | 能力 | 覆盖 App 数 | 说明 |
|---|---|---|---|
| **Top（接收分享家族）** | 任意文件 / 图片 / 文字 / 视频 / 多文件 | 68 / 59 / 48 / 40 / 38 | **同一个 `ACTION_SEND(_MULTIPLE)` 门**——覆盖面最广 |
| 中档 | 处理选中文字(**12**) / 当文件选择器(11) / 打开 PDF(8) / 网页搜索(8) | — | 12 个 App 已有 `ACTION_PROCESS_TEXT` |
| 长尾 | 打开视频(5) / 音频(4)；打开网页链接·建日程·发邮件·发短信·地图导航 各(2) | — | 覆盖面小 |
| 独苗（各 1） | 拍照·建联系人·拨号·设闹钟·设计时器·录音·设壁纸·编辑图片·语音识别·TTS | — | 单点能力 |
| **零** | **建备忘 0 / 扫码 0** | — | **能力不存在，不是"没做"** |
> 要点：**覆盖面最广的是"接收分享"家族；"发出去 / 代理"类能力 ≈ 0**。

### 5.2 数据接口七分类（总和 = 183，一项不漏）

| 实测结果 | 数量 | 含义 |
|---|---|---|
| 可读 | **12** | 第三方能读到，且**有数据** |
| 可读·无数据 | 23 | 能读，但实测为空 |
| 需要权限 | 47 | 要签名级权限（拿不到） |
| 未导出 | 88 | 直接锁死 |
| URI 不存在 | 4 | 探测目标无效 |
| 无响应 | 3 | 有声明但不响应 |
| 其它 | 6 | 未归类 |

> **"可读 12" ≠ "不可读 171"**。真正"不为第三方准备的" = 47 + 88 = **135（73.8%）**。真正可用 = 12/183 = **6.6%**。（⚠️ 源 xlsx「说明与方法」第 378 行仍写旧的 12/47/88 三分类，共 147 ≠ 183，**以本表七类为准**。）

### 5.3 深链可靠性分层

- 声明 7084 → 去重 6639 → 聚合 **281 协议**；
- **188（67%）有组件类名依据**（可用）；
- **93（33%）靠路径关键词猜，必须实测**；
- 深链实测样本**仅 58 条**。

## 6. 跨 App 能力模型（本次调研核心新增）

把 §5 的能力事实落成"**什么模式走什么通道**"的映射。三个正交维度：**能力三层** × **五种连接模式** × **通道分级**。

### 6.1 能力三层（机制事实）

| 层 | 机制 | 能干什么 | 可否枚举 |
|---|---|---|---|
| **门** | Activity/Service 的 intent-filter | 让别的 App "**跳进来**" | ✅ 可枚举 |
| **数据** | ContentProvider | 让别的 App "**把数据取出来**" | ✅ 可枚举（但**实测多数锁死**） |
| **参数** | 深链的 host + path | 跳进去之后**带什么** | ✅ 可从 `dumpsys package` 解析 |

### 6.2 能力三层 × 五种模式 → 通道映射（核心表）

| 连接模式 | 一句话 | 主要落点（三层） | **合法通道（1–4）** | 需下探通道（5–6） | 主包内？ |
|---|---|---|---|---|---|
| **收拢** | 把散在 N 个 App 的东西汇到一处 | **门**（接收分享家族）+ **数据**（系统标准数据） | 通道 2（分享/Intent）+ 通道 1（服务层）+ 通道 4（通知监听，官方权限） | — | ✅**主推** |
| **搬运** | A 的东西加工后进 B | **门**（`ACTION_SEND` / `ACTION_PROCESS_TEXT`） | 通道 2（分享 / 选中文字菜单）+ 通道 3（剪贴板） | — | ✅**主推** |
| **编排** | 一句话触发跨多 App 一串动作 | **门 + 参数**（深链 verb 表） | 通道 2（深链/Intent） | — | ✅**主推** |
| **理解** | 不连 App，连它背后的服务 | 服务层 API | 通道 1（API/网页） | — | ✅ |
| **代理** | 替你进某 App 里操作 | 屏幕语义树（本仓库已实现） | —（无合法门：微信"发出去"门 = 0） | **通道 5（无障碍）+ 通道 6（Shizuku）** | ❌ **侧载进阶包** |

### 6.3 三条铁律（写进任何后续设计）

1. **能跳进去的多开着，能取出来的多锁着** —— 所以"收拢/编排"靠"门 + 参数"，**不靠"读别的 App 的数据"**。
2. **产品好不好 = 能不能尽量待在 1–4 层，只在必要时下到 5–6。**
3. **代理模式 = 侧载进阶包**：模式**保留在能力模型里**（不删），代价明确写：**微信封号 + 不可上架 + 每次重启重授权**；**不进主包承诺**。

### 6.4 通道分级（替换旧"上架/不上架"二分法）

| 级别 | 通道 | 代价 |
|---|---|---|
| 1 | 服务层（API / 网页） | 无，最稳 |
| 2 | 官方 Intent / 分享 / 深链 | 无，**可上架** |
| 3 | 剪贴板 | 无，需用户手动粘 |
| 4 | 通知监听（官方权限） | 低，可上架 |
| 5 | 无障碍（模拟点屏幕） | **封号、上不了架** |
| 6 | Shizuku | 侧载，**每次重启要重授权** |

> 目标愿景：**tier5–6 占比越低越好**（作为一条可观测的北向健康度指标，见 §5.6）。

## 9. 时间线 & 里程碑

> 作者：路径（roadmap-planner）｜输入：需求池（析客定稿 REQ-01~17）· `docs/worklog/*`（已跑通实现与非缺口）· `deliverables/workbuddy-改版简报-2026-10-10.md` · `deliverables/android-capability-inventory/`
> 写死的前提（不越界）：产品 = **跨 App 连接层**；通道分级 **1 服务层/网页 · 2 官方 Intent/分享/深链 · 3 剪贴板 · 4 通知监听 · 5 无障碍 · 6 Shizuku**，好产品尽量待在 1–4；**分发路线**与**"第一步做什么"均【待拍板】**，本文只并列选项与影响面、不替用户决定；**不删除任何能力项**，不确定的写"进阶包/待验证"；`docs/worklog/` 里已跑通的实现（Shizuku 屏幕自动化、语义树读取三件套、`web_search/web_fetch/enrich_list`、`confirm_plan`、任务级只读作用域、`catalog` 工具目录）一律按"已有"计，不按"设想"计。

### 9.1 优先级评审

**P0（8 项）——连接层的地基。** P0 排在最前不是"更赚钱"，而是**没有它，"跨 App 连接"这件事在架构上无法表达**。它们共同构成一条最小闭环：**能发现有什么可用（REQ-01）→ 有三个把外部内容送进来的门（REQ-02/03/04）→ 能收拢系统标准数据（REQ-05）→ 编排不中途爆预算（REQ-06）→ 模型可换/可控成本（REQ-08）**。端侧窄域路由（REQ-07）是 L，天然跨里程碑，不占 M1 关键路径。

- **REQ-01 能力发现**是 **REQ-02/03/04 的共同底座**：不先枚举"这台手机上谁声明了接收分享 / 处理选中文字 / 有深链"，后面三个入口只能靠硬编码猜测。伏笔已在（`app.config.ts` 的 `<queries>` 已含 intent 条目；能力矩阵 234 App × 28 项已实测落库；`catalog` 工具目录已跑通）。
- **REQ-06 步数预算**是 **REQ-04 深链执行"编排可用性"的前提**：默认 `maxSteps=12`，而一个跨应用任务顺利也要 11–16 步——不加预算机制，深链编排必然"跑到一半停住"。注意 worklog 的结论：**解法不是调大数字，而是减少步数**（专用取→写工具 / 一次读多屏），调大只是最后手段。
- **REQ-02/03/04 是三条并列入口**，不是一条的三种皮：分享（内容已在手上）、选中文字（上下文最轻）、深链（一句话跳到目标页）。REQ-03 是 S（改造最小），REQ-04 是 L（281 协议里 93 条靠猜、需实测）。

**P1（5 项）——信任层，本质是给 P0 和"代理"上闸门。**
- **REQ-11 发送前收件人核对**是全链路**风险最高**的一步：在 B 应用搜昵称会返回多个相似结果，选错人一按发送**不可撤销**。它**只在存在"发送/代理"路径时才成为硬前置**——因此应与 REQ-16（代理）同批落地，而非提前。
- **REQ-12 写入后回读核对（S）**性价比最高：纯 JS、可单测、不依赖设备，且**直接兑现"陈述由代码从实际执行的事实生成"这条硬约束**（当前 `screen_type` 打完字只返回 `{ok}`，键盘只读/粘贴被拒/失焦三种失败看起来和成功一样）。建议随 M1 一起落。
- **REQ-10 一次逻辑确认**与 **REQ-09 可回看审批面板**是同一信任面的两半（前者防"逐文件弹窗训练用户盲点同意"，后者是竞品也没有的差异点）；**REQ-13 埋点**是 REQ-06/07/16 达标与否的度量前提，宜早不宜晚。

**P2（4 项）——生态与可移植，且强依赖"分发路线"拍板。**
- **REQ-16 代理模式**：模式**必须保留**，但**不进主包承诺**，归侧载进阶包（代价：封号 + 不可上架）。它是 REQ-11 的绑定项。
- **REQ-14 Skill 包 / REQ-15 换机迁移**：对应 G3 可移植护城河，是 M2 的硬前置，但都依赖一个稳定的运行时（先有 P0/P1）。
- **REQ-17 进阶包分发开关**：是"双构建"路线的使能项——**只有先拍板走双构建，它才有意义**（见 §9.5）。

**需提请注意（不重排、仅标注）**：REQ-11/12 严格说属"安全闸门"而非普通 P1；若未来主包或进阶包启用任何"发送/写入"类路径，二者应视为该路径的**发布硬前置**。分层权归析客，此处只做依赖提示。

### 9.2 第一步候选对比（A/B/C/D 并列，不排序）

| 候选 | 证据（来自实测/仓库） | 工作量 | 通道层级 | 风险 | 最快可见价值 |
|---|---|---|---|---|---|

### 9.4 风险时序

| 风险 | 触发时点 | 应对（含"若不计政策约束，能力是否成立"） |
|---|---|---|
| **分发路线未拍板** | M0/M1 起步前 | 用已存在的 `MOBILECLAW_PLAY_SAFE` 开关做**双构建技术预演**，把两选项的成本/通道上限摆出（§9.5），**等拍板**；拍板前所有涉及 5/6 层的 REQ（REQ-16、REQ-07 端侧强约束项）默认标"进阶包/待验证"，不进主包承诺 |
| **代理封号 / 不可上架** | M2（REQ-16） | 代理**只进侧载进阶包**、不进主包；显式引用竞品证据（Operit 明示"微信会扫描、严重封号"）。**若不计"封号/不可上架"，代理技术上是成立的**（shell 身份能拿到语义树，已跑通）——所以这是**分发选择，不是技术否决** |
| **深链 93 条靠猜、需实测** | M1/M2（REQ-04） | 先只发 **188 条有组件类名依据**的；93 条走真机实测脚本（`collect-deeplinks.ps1` 可重跑）补录，**未实测的不进对外承诺**；表述上区分"有依据"与"靠猜" |
| **SAF 授权摩擦** | M1（REQ-02/REQ-05） | 分步授权引导 + 监控授权转化；退化路径 = 应用私有区 + "改完再分享/保存"，**不承诺把结果原地写回来源 App**（分享面板只给临时读权） |
| **端侧窄域路由准确率** | M2（REQ-07） | 先做 3 周 spike 拿实测准确率/延迟；不达标则**退守云模型窄域路由**（配合 REQ-08 BYOK），端侧作为"可选"而非承诺 |
| **Kotlin 从未编译 / APK 从未构建** | **M0 起步即触发** | 排为 M0 第一件事：`setup-toolchain.ps1` → `build-local.ps1 -Variant debug`，第一次大概率报错（导入名/API 名）。两个已知坑（266 MB AAR 读超时、路径含非 ASCII）已临时绕过，**但 prebuild 会覆盖**，须做成 config plugin |
| **无障碍 / Android 17 AAPM** | M2+ | 本产品**本就不走无障碍**。**若不计政策约束**：AAPM 封的是"非无障碍工具调用 Accessibility API"，而 shell 语义树路线**不受 AAPM 影响**——所以"用 Shizuku 读语义树"与 AAPM 不是同一问题，不能用它证明该选哪条通道 |
| **订阅 / 成本** | M1 起持续 | 成本**不是门槛**：模型价 3 年降 95–99%，重度自填 key 月成本约 ¥5–30；REQ-08 BYOK 让用户自付、端侧路由降 token。若走订阅，需先定"免费层给什么"，否则会与"零门槛"G1 冲突 |

> 纪律：凡"因政策 X 不做 Y"的条目，均已补"若不计 X，Y 是否成立"——结论是：代理（Y=代理模式）与语义树读取（Y=shell 读屏）**技术上均成立**，属分发/合规选择，不属能力缺口。
